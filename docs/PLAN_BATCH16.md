# 并行推理 / batch-16 设计文档

> 目标：引擎支持**最大 batch 16** 的并发推理，即最多 16 个任务真正同时推前向，而不是排队。
> 本文记录为什么并行轴必须是**批维度**、第一轮实测否决了什么、以及接下来要怎么做。

---

## 1. 为什么并行必须做在批维度上

上一轮已实测（`loop/state.json` round 54）：

| 方式 | 结果 |
|---|---|
| 单进程 + 3 个并发请求 | 结束时间 2.73 / 5.38 / 7.96 s 规则阶梯，总墙钟比 **1.03** —— 完全串行 |
| **两个进程**各服务一个请求 | 4.18 / 4.60 s，对比单进程服务两个 2.21 / 4.53 s，**加速比 0.99×** |

**关键区分**：

* **进程级并行不共享权重读取** —— 两个进程各自流式读同一份 14.4 GB，只是把同一份 DRAM 带宽对半分，所以没有任何收益（还白吃 15 GB 内存）。
* **批级并行共享权重读取** —— 一次前向流式读 14.4 GB，如果这**同一次读取**能同时服务 16 条序列，就等于把权重带宽摊到 16 个 token 上。

**⇒ 所以并行化的唯一正确轴是批维度，理论上限是把 30.9 ms/token 的单序列解码变成 16 token/次扫描。**

## 2. 现有架构：单序列假设在哪里

改造面已经完全摸清（`crates/qw-model/src/runner.rs`）：

| 组件 | 现状 | batch-16 需要 |
|---|---|---|
| 投影（占成本 ~86%） | **已经是按 `TILE` 行批处理的**（`encode_tile` → `encode_k`，grid = `out_f*32`，每个 threadgroup 负责一个输出行、消费 TILE 个 x 行） | 把行数提到 16，并且每行带自己的 `(seq, pos)` |
| `FullAttn::k_cache/v_cache` | `[n_kv][max_t][head_dim]`，隐含单序列 | `[B][n_kv][max_t][head_dim]` |
| `Gdn::state` | fp32 `[Hv][Dv][Dk]`，单序列递推态 | `[B][Hv][Dv][Dk]` |
| `Gdn::window` | `[conv_ring][conv_dim]`，按 `p % conv_ring` 索引 | `[B][conv_ring][conv_dim]`，按 `(seq, pos % ring)` |
| rope / kv_append / attn_scores | 用 `pos + row`（同一序列的连续位置） | 每行传入自己的 `pos` |
| `run_job` | 每个请求开头 `model.reset()` | 每序列一份状态，互不干扰 |
| 调度 | 单引擎线程 + `mpsc` 串行 | 16 路组批，连续批处理 |

**⇒ 最关键的好消息**：真正吃带宽的投影部分**已经具备批行结构**，不需要从零写 GEMM。

## 3. 第一轮：把 u4hx 加宽到 16 行 —— **已证伪**

### 3.1 做了什么

新增 MSL 宏实例 `Q4_GEMV_KS_U4HX(q4_gemv_k16_u4hx, 16)`（每个 threadgroup 仍负责一个输出行，但消费 16 个 x 行），并新增两个验证设施：

* `qwen38 check --rows N`：把 N 个**互不相同**的激活送进一次权重读取，**每一行都对各自的 CPU 参考**验证（互不相同的输入意味着任何跨行串扰都会暴露成数量级错误，而不是末位差异），同时报告与独立单行内核的差异与计时。
* `qwen38 bench --rows 18 --tokens 16`：全模型 14.4 GB 上的**配对**对比——1 次 k16 扫描（16 token）对 16 次单行扫描（16 token），同进程内交替以抵消热漂移。

### 3.2 结果一：数值正确 ✅

`check --rows 16` 在 8 个代表性张量（MLP / 线性注意力 / 全注意力 / lm_head）上**全部通过**，norm_err 0.27%–1.39%，
Metal JIT 编译仅 **159 ms**。批量行的算术是通的。

### 3.3 结果二：性能被否决 ❌

`bench --rows 18 --tokens 16`（配对偏差标定 0.994，方法可信）：

| 方案 | ms/扫描 | tok/s |
|---|---|---|
| **k16：16 token 来自 1 次权重读取** | **635.60** | **25.2** |
| k1 × 16：每次权重读取出 1 token | 494.13 | 32.4 |
| k16 重复（仪器偏差） | 632.02 | 25.3 |

**一次 k16 扫描是 20.6 倍于一次单行扫描**（635 ms vs 30.9 ms），产出的却是 16 倍 token —— 也就是**摊销完全没有发生，整批反而比串行慢 22%（0.78×）**。

一次 k16 扫描的有效带宽只有 22.7 GB/s，而单行扫描是 466 GB/s（接近 DRAM 峰值）。
**⇒ 该内核不是带宽受限，而是算力/访存指令受限。**

### 3.4 根本原因（这决定了下一版怎么做）

看内层循环：每处理一个权重块（8 个权重 = 2 次 uint4 载入），

* **k1 内核**：发 **1** 次 x 载入（16 字节）→ 2 个 dot。
* **k16 内核**：发 **16** 次 x 载入 → 32 个 dot。

**⇒ x 的访存指令数随 NK 线性增长，而权重载入数不变。** 字节数确实是权重占绝对多数（14.4 GB 对几十 KB），
但**指令数**被 x 载入主导（16 次对 2 次）。内核于是从带宽受限退化为访存指令受限，
再加上 16 个活跃累加器带来的寄存器压力，才有了那 20.6 倍。

**结论：不能靠"每个线程多扛几行"来摊销权重。** 摊销必须发生在**不同线程之间**，而不是同一个线程内部。

## 3.5 第二版（第 2 轮）：L2 共享 —— **成功** ✅

按 §3.4 的结论，把并行从"线程内部"挪到"线程之间"：**内核体与 `q4_gemv_hx` 逐行相同**
（1 个累加器、每权重块 1 次 x 载入、2 个 dot），只把 threadgroup id 拆成两半：

```
row = tg / 16      // 输出行
xr  = tg % 16      // 第几条激活
grid = 16 * out_f 个 threadgroup
```

于是**16 个连续 id 的 threadgroup 共用同一权重行**：DRAM 供应一次，其余 15 次命中 L2，
而每个线程的形状完全没变（无寄存器压力、无额外访存指令）。

**数值正确性**：`check --rows 16` 八个张量全过，norm_err 0.27–1.39%，
与 k16 版本**完全一致**（同一累加顺序），Metal JIT 仅 **24 ms**（k16 是 159 ms）。

**性能**（`bench --rows 18 --tokens 16`，全模型 14.4 GB，同进程交替，四臂）：

| 臂 | ms/扫描 | tok/s | vs b16 |
|---|---|---|---|
| **b16 网格共享，1 次权重读取** | **306.45** | **52.2** | 1.000x |
| k16 每线程扛行，1 次权重读取 | 634.04 | 25.2 | 0.483x |
| k1 × 16 串行，16 次权重读取 | 482.89 | 33.1 | 0.635x |
| b16 重复（仪器标定） | 289.83 | 55.2 | 1.057x |

**⇒ b16 比串行快 1.666×（校准后）**，16 路并发聚合 **52.2 tok/s**。
k16 那条路线在同一轮里再次确认失败（0.483×）。

单行扫描是 482.89/16 = 30.2 ms，而 b16 扫描是 306.45 ms —— **10.2× 而非 16×**，
说明权重摊销**已经真实发生但只覆盖了一部分**（完美复用应当是 ~30–35 ms）。

### 为什么还没到 16×：L2 带宽才是现在的墙

按"一个 threadgroup 负责一个输出行"的分解，每个输出元素都要读完整条 x，
所以 x 的 L2 流量 = `Σ out_f × K × 2 字节`：

| | x 的 L2 流量/扫描 | 权重流量 | 实测耗时 | 反推 L2 带宽 |
|---|---|---|---|---|
| k1 单次 | ~57.6 GB | 14.4 GB (DRAM) | 30.2 ms | ~1.9 TB/s |
| b16 | ~921 GB | 14.4 GB (DRAM) + L2 复用 | 306 ms | ~3.0 TB/s |

**⇒ b16 已经把 L2 推到 ~3 TB/s 量级，接近这个分解方式的上限。**

### 下一个杠杆：分块重用 x（GEMM 式 tiling）

要再往上，必须**减少每个输出行对 x 的重复读取**，标准做法是把 x 分块放进 threadgroup memory，
让一个 threadgroup 一次算多行输出：

* 一个 threadgroup 同时算 **R 个输出行**，x 只从 L2 读一次、在寄存器里复用 R 次
  → x 的 L2 流量直接降到 **1/R**；
* R=4 时 L2 流量从 921 GB 降到 ~230 GB，理论上把 306 ms 压向 DRAM 底噪。

代价是每线程要持有 R 个累加器 —— 但注意这与 §3 失败的 k16 **不同**：
k16 是 R=16 个**激活**、每个权重块要发 16 次 x 载入；这里是 R 个**输出行**共用同一次 x 载入，
方向相反，寄存器压力也小得多（R=4 时 4 个累加器）。这正是 `q4_gemv_k3_r*` 系列当年试探过的方向。

## 4. 下一版设计：L2 共享权重、每线程仍只扛一行

核心思路：**保持 k1 内核的每线程结构不变（1 个累加器、每个权重块 1 次 x 载入），把"同一权重行服务 16 个 x 行"这件事交给 L2 和线程组调度顺序。**

```
grid = 16 * out_f 个 threadgroup
tg    = threadgroup_position_in_grid
row   = tg / 16        // 输出行
xr    = tg % 16        // 第几条序列的激活
// 内核体与 q4_gemv_hx 完全一致，只是
//   x 基址 = x + xr*K
//   y 写入 = y[xr*out_f + row]
```

* 每个权重块：**1 次权重载入 + 1 次 x 载入 + 2 个 dot** —— 与 k1 完全相同，**没有额外寄存器压力，没有额外访存指令**。
* 16 个**连续 id** 的 threadgroup 共用同一权重行。GPU 大致按 id 顺序调度，它们会几乎同时在不同核心上执行，
  于是该权重行**从 DRAM 只读一次、从 L2 供其余 15 次**。
* 预期：耗时接近**一次** k1 扫描（~30.9 ms），却产出 16 个 token —— 理论 ~16× 吞吐。
* **风险（也是要测的东西）**：L2 是否真的兜住这 16 次复用。若兜不住，DRAM 流量退回 16×，
  结果**退化到与串行相同**（不会更差），这是有下限保护的赌博。

备选方案（若 L2 复用不成立）：把权重块用 threadgroup memory 协作暂存，threadgroup 内 16 个 warp 各负责一条 x 行。
代价是共享内存带宽被放大 16 倍，收益不确定，所以放在第二顺位。

## 5. 验收门禁（后续每轮都要过）

1. **数值**：`check --rows 16` 八个张量全过（每行对各自 CPU 参考，norm_err < 5%）。
2. **批 vs 串行**：`bench --rows 18 --tokens 16` 的校准后加速比 **> 1.0**，且配对偏差接近 1.0。
   （当前 0.78×，必须先越过 1.0 才值得继续往下做。）
3. **批 == 独立运行**：16 条序列组批解码出的 token，必须与各自单独解码一致。
   注意：批量行与单行是**不同的求和顺序**，末位可能有差（`check` 的 `bits!=` 列已经量到这一点），
   所以这条门禁应当和现有 `spec==plain` 一样按"实际输出 token 一致"来判，而不是逐位比较。
   **这也意味着 batch-16 会继承 `spec==plain` 那个未决问题的风险**（见 `loop/state.json` 的
   `open_issues/spec-plain-intermittent`），该问题应在批量功能上线前查清。
4. **端到端**：16 个并发请求的墙钟接近 1 个请求（而不是 16 倍），且总吞吐显著高于串行。
5. **回归**：现有 `accept.sh` 12 项全过；单序列路径的吞吐不得下降。

## 7. 第三轮：每序列状态分区 —— **已完成并用门禁锁住** ✅

调度器、批量前向、并发服务**三者共同的前置条件**是：模型必须能同时持有 16 条序列的状态。
所以先把这一层做掉。

### 做法：字节偏移，内核一行不改

`forward2` 逐行读一遍发现，单行路径 `forward` 里真正触碰**序列状态**的只有 **8 个位置**：
KV 追加、attention 打分、attention 输出、qkv 写入卷积环、卷积读取、GDN 递推态。
于是**给每条序列一个字节偏移**就足够了：

```
kv_off   = seq * kv_stride      // KV cache
win_off  = seq * win_stride     // 卷积环
st_off   = seq * state_stride   // GDN 递推态
```

* 状态缓冲区一次性按 `batch` 份分配（`state` / `window` / `snap` / `k_cache` / `v_cache`）；
* 每个 dispatch 用 `buf_offset(i, buf, seq * stride)` 把该序列的切片交给内核；
* **从内核里看，缓存就是从这条序列的切片开始的** —— 所以 **MSL 内核完全不用改**，
  也不需要把 `seq` 传进内核。

新增 `Qwen38::load_batch(dir, max_t, batch)`；`load(dir, max_t)` 保持原样（= `batch 1`），
所以所有既有调用点零改动。`QW_BATCH=16` 走批量分配（代价是 16 倍状态内存，主要是 KV cache，
所以是 opt-in 而不是默认）。

### 门禁：同一 prompt 在不同 slot 必须逐字节相同

`QW_SLOT=<n>` 让一次前向跑在第 n 条序列的状态上。偏移只要错一点，
slot 7 就会读到/写坏别的内存，输出**必然**立刻发散。实测：

| 配置 | 输出 |
|---|---|
| 基线（无 QW_BATCH） | `greedy_ids: [1358, 760, 6511, 314, 9338, ...]` |
| `QW_BATCH=16`（slot 0） | **完全相同** |
| `QW_BATCH=16 QW_SLOT=7` | **完全相同** |
| `QW_BATCH=16 QW_SLOT=15` | **完全相同** |

同时 `verify --oracle` 保持 parity 6/6 —— 默认路径（batch=1，偏移恒为 0）行为逐字节未变。

### 注意：这一轮**还没有**做到的事

* **前向仍是一次一条序列**。`forward_seq(seq, pos)` 一次只推一个 token，
  所以现在还不能"一次前向同时推进 16 条"——那需要把行数提到 16
  （投影用 §3.5 的 b16 内核，scratch 缓冲区从 `TILE=4` 扩到 16，逐行操作用每行的 `(seq,pos)`）。
* **MTP 草稿头仍是单序列的**（`Mtp::load` 没有 `batch` 参数），批量服务先用纯解码路径。
* **slot 复用需要 `reset_seq`**：新请求进入某个 slot 前必须把该 slot 的状态清零，
  目前只有整体 `reset()`。
* **调度器与服务端未改**：`Engine` 仍然一次一个 Job。

## 8. 第四轮：批量前向打通 —— **一次前向同时推进 16 条，且逐位等价** ✅

上一轮把状态切成了 16 份，但一次前向仍只推一条。这一轮把前向本身变成批量的。

### 做法

`forward2(pos)`（原本的 TILE=4 投机验证通路，结构正好是"投影批处理 + 逐行操作"）
泛化成 **`forward_rows(rows: &[(usize, usize)])`**，行 `i` 属于序列 `rows[i].0`、位置 `rows[i].1`：

* **投影**：整块 14.4 GB 权重**只读一次**，服务全部 16 行 —— 这正是整件事的意义；
* **逐行操作**（rope / kv_append / attn / GDN）：每行按 `seq` 取自己的状态切片。

### 过程中被门禁抓到的一个真 bug

`kernels.q4_gemv_tile` 是**编译期 4 行特化内核**（`K4_U4HX`）。
把 n=16 传进去，它**只投影前 4 行**，其余 12 行的隐状态从未被写入。
门禁的表现非常典型：**slot 0–3 全对，slot 4–15 全部输出 token 0**。

修法就是第 2 轮设计好的 b16 网格共享内核：新增 `QLinear::encode_rows`，
按行数选内核（`≤ TILE` 走特化内核，`> TILE` 走 16 行网格内核）。
**13 处投影全部改为按行数分派**。

### 另一处结构改动：卷积必须逐行

tile 宽的卷积内核在整块 tile 上**共享一个卷积环**——这对投机验证是对的
（同一序列的连续 4 个位置），对批量服务是错的（16 条序列各有自己的环）。
所以改成**逐行卷积**：先把每行的原始 qkv 从 staging 搬进它自己的环槽，再卷积。
搬运用现成的 `copy_off`（带元素级双偏移），没有新增 MSL。
于是 tile 宽卷积内核变成死代码，已删除。

### 配套

* scratch 缓冲区从 4 行加宽到 `BATCH_MAX = 16`；
* `reset_seq(seq)`：只清零**一条**序列的 GDN 递推态与卷积环，让 slot 可回收。
  **KV cache 不需要清零**——它是位置索引的，`pos` 之后的表项永远不会被读到，
  所以每个 slot 的清理量从 ~700 MB 降到 ~165 MB；
* 新增 `qwen38 batch-check` 门禁。

### 门禁结果：**逐位等价**

`batch-check` 分两阶段：先让 16 个 slot 吃同一 prompt，
再**用 16 个互不相同的 token 让状态分叉**（只有分叉之后，"偏移写错时所有 slot
互相一致"这种假通过才不可能发生），然后逐个与"该 slot 单独跑"对比：

| slots | 结果 | worst \|logit diff\| |
|---|---|---|
| 16 | 16/16 贪心 token 一致 | **0.0000** |
| 4 | 4/4 贪心 token 一致 | **0.0000** |

**差值是 0** —— b16 内核的逐行累加顺序与单行内核相同，所以批量服务**不改变任何输出**，
不只是"token 相同"，是 logits 逐位相同。

### 这一轮之后还差什么

* **服务端还没用上它**：`Engine` 仍然一次一个 Job。调度器要把 16 路组批接上
  （这是下一轮）。
* MTP 投机解码仍是单序列的（`Mtp::load` 没有 `batch`），所以批量路径跑纯解码。
* 教程要在服务端真正并发之后再改写（目前仍如实写着"并发 = 1"）。

**注意工程顺序**：本轮之前我算过一笔账——**先做 round-robin 调度器是严重倒退**。
plain decode 每 token 30.9 ms，16 条轮转一轮要 494 ms，单个请求会慢 **21 倍**。
所以批量前向是硬前置：没有它，"并发"只是把吞吐平摊而不是提升。
现在批量前向已经逐位等价，接调度器才是纯收益。

## 9. 第五轮：服务端接上批量前向 —— **16 路真并发落地** ✅

### 引擎结构

`Engine` 线程不再是"取一个 Job、跑完、再取下一个"，而是持有 **16 个槽位**：

```
每轮：
  1. 接纳 —— 空闲槽 + 排队中的请求，reset_seq(slot) 后入槽
  2. 每个能推进的槽各贡献一行 (slot, pos)：
       预填充阶段 -> 喂 ids[pf]，位置 pf
       解码阶段   -> 喂上一轮算出的 feed，位置 pos
  3. 一次 forward_rows(&rows) —— 整块 14.4 GB 权重只读一遍
  4. 按行读回 logits，argmax 得到各槽的下一个 token，增量解码并推送文本
  5. 已结束（EOS / 用完 max_tokens）的槽 flush 后回收
```

接纳策略：**完全空闲时才阻塞等待**，否则只取已经到达的请求 —— 一批同时打进来的请求
会被组进同一个 batch，而不是一个一个串行跑掉。

一个真实存在的边界条件：`forward_rows` 在 n > TILE 时要求各行属于**不同序列**
（卷积环只能装 conv_k 行 + 本轮写入的行，一序列一位置满足，同序列连续 16 个位置不满足），
越界会 `ensure!` 报错而不是静默算错。

### 门禁：`tools/conc.sh`

16 个**互不相同**的请求（共用 prompt 会是弱测试 —— 所有槽读同一份状态也能互相自洽）：

| | 总墙钟 | 平均每请求 |
|---|---|---|
| 16 并发 | **22.02 s** | 1.38 s |
| 16 串行 | 73.36 s | 4.59 s |

**加速比 3.33×，16/16 响应与单独跑逐字节一致。**

达不到 16× 的原因要说清楚，否则是自欺：一轮 pass 的代价随 batch 上升
（16 行一轮约 306 ms，是单行 ~30 ms 的 **10.2 倍而不是 16 倍**，这是内核自身的效率上限），
而且各请求生成长度不同，先结束的槽空出来后剩下的仍按轮推进，尾部利用率低。
**换来的正确性代价是零**：`batch-check` 已证明批量前向与独立前向逐位等价。

### 顺带修掉的一个测试脚本 bug（值得记下来）

第一次跑 `conc.sh` 时并发阶段 16 个响应全部正确返回，但脚本随后挂死 20 分钟、
CPU 0%、且单独发一个新请求 3.3 秒就正常返回。原因不在引擎：
**服务端是脚本的后台作业，而 `wait`（不带参数）会连它一起等**，于是永久阻塞。
改成收集 curl 的 PID 后 `wait "${pids[@]}"` 即正常。
**诊断时"响应文件已写全 + 进程 CPU 为 0 + 新请求正常"这三条同时成立，就说明卡的是脚本而不是服务。**

### 这一轮之后仍差什么

* **MTP 草稿头的批量化**：批量路径跑纯解码，投机解码关闭。单请求串行时投机带来的
  ~30% 单流加速，在 16 路并发下被换成了总吞吐 —— 这是有意的取舍，但还没做到两全。
* 单个槽内的投机（只在槽数 == 1 时走投机路径）是可行的下一步。

## 10. 服务器可用性修复：内存预估（用户实测踩到）✅

用户在 16 路并发版上执行 `serve --max-ctx 1000000`，然后 `curl` 得到
`curl: (7) Failed to connect to 127.0.0.1 port 8080`。

### 根因

进程**被系统 SIGKILL**（`exit=137 / Killed: 9`）：权重加载正常，随后在分配 KV cache 时内存爆掉。
KV cache 是 `batch * nkv * max_t * hd * 2` 每层、共 16 个 full-attention 层，
即 **64 KB/token/slot**；16 个 slot 一起分配 → `1000000 × 64 KB × 16 ≈ 1 TB`，而机器是 128 GB。
**端口从未绑定**，所以 curl 只能报连接被拒，日志里连一句错误都没有 —— 这是最难查的那类故障。

### 修复

`load_batch` 在读入 config **之后、碰任何权重之前**调用 `check_memory`：

* 建模 `weights + per_slot×batch + per_token×max_t`（含 MTP 头与 scores 缓冲）；
* 与物理内存的 85% 比较，超了就 bail，并给出具体构成、**这台机器在 batch=16 / batch=1 下
  分别能放到多少**，以及模型自身的 262144 上限；
* 校验点刻意放在加载权重之前 —— **失败要在几秒内发生，不能等 10 秒加载完再死**。

### 两个值得记的细节

* **两处数字一开始写错了**：把 `per_token * max_t` 当成了固定开销，报出"0 GB of weights"，
  又把**整批**的每 token 开销（1029 KB）标成了"per slot"（真实是 64 KB/slot）。
  错误信息算错比没有错误信息更坏 —— 它会把人引到错误方向。
* **估算需要一个实测校准**：量了 ctx 8192（41 GB）与 ctx 32768（65 GB）两点，
  得到**实测斜率 1.0 MB/token**（模型算 1.005 MB，几乎完全吻合），
  但固定开销实测 33 GB 而模型只有 26 GB —— 差的 ~8 GB 是 Metal 驱动与加载期 staging，
  不在任何显式缓冲区里。于是加了 `MEM_OVERHEAD = 8 GB`，
  建议值从 83782 收敛到 **75634**（实测上限约 77315，略保守即安全）。

## 12. Prefix Cache：KV 复用与命中率上报（第 8 轮）

### 为什么几乎不需要额外的存储

引擎有两个性质让前缀缓存变得非常轻：

1. **KV cache 从不被清零**——`reset_seq` 只回退 delta-net 状态和卷积窗口，位置是按需写入、
   只读到当前位置为止；
2. **delta-net 状态是递推量**，只在槽位被无关 prompt 复用时才需要归零。

所以如果一个新 prompt 的开头**恰好等于某个槽位已经消费过的 token 序列**，那个槽位
**本来就已经处在正确状态**，整个前缀可以直接不重算——不需要快照、不需要拷贝、不需要淘汰策略。

### 实测（6.9K prompt，与 OpenCode 的实际规模一致）

| 请求 | TTFT | 结果 |
|---|---|---|
| 1. 冷启动 | **230.41 s** | miss，全量 prefill |
| 2. 完全相同的重试 | 324.36 s | **miss**（见下） |
| 3. **agent 下一轮**（prompt + assistant 回复 + 新 user 轮） | **1.38 s** | **HIT，跳过 6875/6890 token** |

引擎日志：

```
slot 0: prefix cache HIT - skipped 6875 of 6890 prompt tokens (100%),
        cumulative KV hit rate 33.3% of 20622 tokens over 3 request(s), 1 reused
```

**230 s → 1.38 s，167 倍。** 这正是 agent 框架产生的形态：每一轮都把整个对话重发一遍，
所以除第一轮外，prompt 的绝大部分都已经在槽位里了。

### 命中率为什么按 token 加权上报

按"请求数"算命中率会掩盖真实成本：一个复用了 90% prompt 的请求算一次 hit，但两个请求
各做一遍全量 prefill 也会显示 50%。所以**上报的是 token 加权的复用率**，同时给出
请求计数。

### 已知限制：完全相同的重试会 miss

解码之后槽位的状态位于 `prompt + 已生成` 这个位置，**已经越过 prompt 边界**。
而重试发送的 prompt 只有原来的 `prompt`，比状态的历史短——递推状态无法回退到中间位置，
所以只能 miss。

要覆盖这个场景，需要在 **prefill 结束的那一刻**存一份 `state` + `window` 快照
（每槽位约 179 MB：delta-net 151 MB + 卷积窗口 28 MB），命中边界时恢复即可。
这是下一轮的工作，不影响 agent 主路径。
