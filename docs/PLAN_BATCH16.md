# 并行推理 / batch-16 设计文档

> 目标：引擎支持**最大 batch 16** 的并发推理，即最多 16 个任务真正同时推前向，而不是排队。
> 本文记录为什么并行轴必须是**批维度**、第一轮实测否决了什么、以及接下来要怎么做。

---

## 1. 为什么并行必须做在批维度上

上一轮已实测（`loop/state.json` round 54）：

| 方式 | 结果 |
|---|---|
| 单进程 + 3 个并发请求 | 结束时间 2.73 / 5.38 / 7.96 s 规则阶梯，总墙钟比 **1.03** —— 完全串行 |
| **两个进程**各服务一个请求 | 4.18 / 4.60 s，对比单进程服务两个 2.21 / 4.53 s，**加速比 0.99×** |

**关键区分**：

* **进程级并行不共享权重读取** —— 两个进程各自流式读同一份 14.4 GB，只是把同一份 DRAM 带宽对半分，所以没有任何收益（还白吃 15 GB 内存）。
* **批级并行共享权重读取** —— 一次前向流式读 14.4 GB，如果这**同一次读取**能同时服务 16 条序列，就等于把权重带宽摊到 16 个 token 上。

**⇒ 所以并行化的唯一正确轴是批维度，理论上限是把 30.9 ms/token 的单序列解码变成 16 token/次扫描。**

## 2. 现有架构：单序列假设在哪里

改造面已经完全摸清（`crates/qw-model/src/runner.rs`）：

| 组件 | 现状 | batch-16 需要 |
|---|---|---|
| 投影（占成本 ~86%） | **已经是按 `TILE` 行批处理的**（`encode_tile` → `encode_k`，grid = `out_f*32`，每个 threadgroup 负责一个输出行、消费 TILE 个 x 行） | 把行数提到 16，并且每行带自己的 `(seq, pos)` |
| `FullAttn::k_cache/v_cache` | `[n_kv][max_t][head_dim]`，隐含单序列 | `[B][n_kv][max_t][head_dim]` |
| `Gdn::state` | fp32 `[Hv][Dv][Dk]`，单序列递推态 | `[B][Hv][Dv][Dk]` |
| `Gdn::window` | `[conv_ring][conv_dim]`，按 `p % conv_ring` 索引 | `[B][conv_ring][conv_dim]`，按 `(seq, pos % ring)` |
| rope / kv_append / attn_scores | 用 `pos + row`（同一序列的连续位置） | 每行传入自己的 `pos` |
| `run_job` | 每个请求开头 `model.reset()` | 每序列一份状态，互不干扰 |
| 调度 | 单引擎线程 + `mpsc` 串行 | 16 路组批，连续批处理 |

**⇒ 最关键的好消息**：真正吃带宽的投影部分**已经具备批行结构**，不需要从零写 GEMM。

## 3. 第一轮：把 u4hx 加宽到 16 行 —— **已证伪**

### 3.1 做了什么

新增 MSL 宏实例 `Q4_GEMV_KS_U4HX(q4_gemv_k16_u4hx, 16)`（每个 threadgroup 仍负责一个输出行，但消费 16 个 x 行），并新增两个验证设施：

* `qwen38 check --rows N`：把 N 个**互不相同**的激活送进一次权重读取，**每一行都对各自的 CPU 参考**验证（互不相同的输入意味着任何跨行串扰都会暴露成数量级错误，而不是末位差异），同时报告与独立单行内核的差异与计时。
* `qwen38 bench --rows 18 --tokens 16`：全模型 14.4 GB 上的**配对**对比——1 次 k16 扫描（16 token）对 16 次单行扫描（16 token），同进程内交替以抵消热漂移。

### 3.2 结果一：数值正确 ✅

`check --rows 16` 在 8 个代表性张量（MLP / 线性注意力 / 全注意力 / lm_head）上**全部通过**，norm_err 0.27%–1.39%，
Metal JIT 编译仅 **159 ms**。批量行的算术是通的。

### 3.3 结果二：性能被否决 ❌

`bench --rows 18 --tokens 16`（配对偏差标定 0.994，方法可信）：

| 方案 | ms/扫描 | tok/s |
|---|---|---|
| **k16：16 token 来自 1 次权重读取** | **635.60** | **25.2** |
| k1 × 16：每次权重读取出 1 token | 494.13 | 32.4 |
| k16 重复（仪器偏差） | 632.02 | 25.3 |

**一次 k16 扫描是 20.6 倍于一次单行扫描**（635 ms vs 30.9 ms），产出的却是 16 倍 token —— 也就是**摊销完全没有发生，整批反而比串行慢 22%（0.78×）**。

一次 k16 扫描的有效带宽只有 22.7 GB/s，而单行扫描是 466 GB/s（接近 DRAM 峰值）。
**⇒ 该内核不是带宽受限，而是算力/访存指令受限。**

### 3.4 根本原因（这决定了下一版怎么做）

看内层循环：每处理一个权重块（8 个权重 = 2 次 uint4 载入），

* **k1 内核**：发 **1** 次 x 载入（16 字节）→ 2 个 dot。
* **k16 内核**：发 **16** 次 x 载入 → 32 个 dot。

**⇒ x 的访存指令数随 NK 线性增长，而权重载入数不变。** 字节数确实是权重占绝对多数（14.4 GB 对几十 KB），
但**指令数**被 x 载入主导（16 次对 2 次）。内核于是从带宽受限退化为访存指令受限，
再加上 16 个活跃累加器带来的寄存器压力，才有了那 20.6 倍。

**结论：不能靠"每个线程多扛几行"来摊销权重。** 摊销必须发生在**不同线程之间**，而不是同一个线程内部。

## 3.5 第二版（第 2 轮）：L2 共享 —— **成功** ✅

按 §3.4 的结论，把并行从"线程内部"挪到"线程之间"：**内核体与 `q4_gemv_hx` 逐行相同**
（1 个累加器、每权重块 1 次 x 载入、2 个 dot），只把 threadgroup id 拆成两半：

```
row = tg / 16      // 输出行
xr  = tg % 16      // 第几条激活
grid = 16 * out_f 个 threadgroup
```

于是**16 个连续 id 的 threadgroup 共用同一权重行**：DRAM 供应一次，其余 15 次命中 L2，
而每个线程的形状完全没变（无寄存器压力、无额外访存指令）。

**数值正确性**：`check --rows 16` 八个张量全过，norm_err 0.27–1.39%，
与 k16 版本**完全一致**（同一累加顺序），Metal JIT 仅 **24 ms**（k16 是 159 ms）。

**性能**（`bench --rows 18 --tokens 16`，全模型 14.4 GB，同进程交替，四臂）：

| 臂 | ms/扫描 | tok/s | vs b16 |
|---|---|---|---|
| **b16 网格共享，1 次权重读取** | **306.45** | **52.2** | 1.000x |
| k16 每线程扛行，1 次权重读取 | 634.04 | 25.2 | 0.483x |
| k1 × 16 串行，16 次权重读取 | 482.89 | 33.1 | 0.635x |
| b16 重复（仪器标定） | 289.83 | 55.2 | 1.057x |

**⇒ b16 比串行快 1.666×（校准后）**，16 路并发聚合 **52.2 tok/s**。
k16 那条路线在同一轮里再次确认失败（0.483×）。

单行扫描是 482.89/16 = 30.2 ms，而 b16 扫描是 306.45 ms —— **10.2× 而非 16×**，
说明权重摊销**已经真实发生但只覆盖了一部分**（完美复用应当是 ~30–35 ms）。

### 为什么还没到 16×：L2 带宽才是现在的墙

按"一个 threadgroup 负责一个输出行"的分解，每个输出元素都要读完整条 x，
所以 x 的 L2 流量 = `Σ out_f × K × 2 字节`：

| | x 的 L2 流量/扫描 | 权重流量 | 实测耗时 | 反推 L2 带宽 |
|---|---|---|---|---|
| k1 单次 | ~57.6 GB | 14.4 GB (DRAM) | 30.2 ms | ~1.9 TB/s |
| b16 | ~921 GB | 14.4 GB (DRAM) + L2 复用 | 306 ms | ~3.0 TB/s |

**⇒ b16 已经把 L2 推到 ~3 TB/s 量级，接近这个分解方式的上限。**

### 下一个杠杆：分块重用 x（GEMM 式 tiling）

要再往上，必须**减少每个输出行对 x 的重复读取**，标准做法是把 x 分块放进 threadgroup memory，
让一个 threadgroup 一次算多行输出：

* 一个 threadgroup 同时算 **R 个输出行**，x 只从 L2 读一次、在寄存器里复用 R 次
  → x 的 L2 流量直接降到 **1/R**；
* R=4 时 L2 流量从 921 GB 降到 ~230 GB，理论上把 306 ms 压向 DRAM 底噪。

代价是每线程要持有 R 个累加器 —— 但注意这与 §3 失败的 k16 **不同**：
k16 是 R=16 个**激活**、每个权重块要发 16 次 x 载入；这里是 R 个**输出行**共用同一次 x 载入，
方向相反，寄存器压力也小得多（R=4 时 4 个累加器）。这正是 `q4_gemv_k3_r*` 系列当年试探过的方向。

## 4. 下一版设计：L2 共享权重、每线程仍只扛一行

核心思路：**保持 k1 内核的每线程结构不变（1 个累加器、每个权重块 1 次 x 载入），把"同一权重行服务 16 个 x 行"这件事交给 L2 和线程组调度顺序。**

```
grid = 16 * out_f 个 threadgroup
tg    = threadgroup_position_in_grid
row   = tg / 16        // 输出行
xr    = tg % 16        // 第几条序列的激活
// 内核体与 q4_gemv_hx 完全一致，只是
//   x 基址 = x + xr*K
//   y 写入 = y[xr*out_f + row]
```

* 每个权重块：**1 次权重载入 + 1 次 x 载入 + 2 个 dot** —— 与 k1 完全相同，**没有额外寄存器压力，没有额外访存指令**。
* 16 个**连续 id** 的 threadgroup 共用同一权重行。GPU 大致按 id 顺序调度，它们会几乎同时在不同核心上执行，
  于是该权重行**从 DRAM 只读一次、从 L2 供其余 15 次**。
* 预期：耗时接近**一次** k1 扫描（~30.9 ms），却产出 16 个 token —— 理论 ~16× 吞吐。
* **风险（也是要测的东西）**：L2 是否真的兜住这 16 次复用。若兜不住，DRAM 流量退回 16×，
  结果**退化到与串行相同**（不会更差），这是有下限保护的赌博。

备选方案（若 L2 复用不成立）：把权重块用 threadgroup memory 协作暂存，threadgroup 内 16 个 warp 各负责一条 x 行。
代价是共享内存带宽被放大 16 倍，收益不确定，所以放在第二顺位。

## 5. 验收门禁（后续每轮都要过）

1. **数值**：`check --rows 16` 八个张量全过（每行对各自 CPU 参考，norm_err < 5%）。
2. **批 vs 串行**：`bench --rows 18 --tokens 16` 的校准后加速比 **> 1.0**，且配对偏差接近 1.0。
   （当前 0.78×，必须先越过 1.0 才值得继续往下做。）
3. **批 == 独立运行**：16 条序列组批解码出的 token，必须与各自单独解码一致。
   注意：批量行与单行是**不同的求和顺序**，末位可能有差（`check` 的 `bits!=` 列已经量到这一点），
   所以这条门禁应当和现有 `spec==plain` 一样按"实际输出 token 一致"来判，而不是逐位比较。
   **这也意味着 batch-16 会继承 `spec==plain` 那个未决问题的风险**（见 `loop/state.json` 的
   `open_issues/spec-plain-intermittent`），该问题应在批量功能上线前查清。
4. **端到端**：16 个并发请求的墙钟接近 1 个请求（而不是 16 倍），且总吞吐显著高于串行。
5. **回归**：现有 `accept.sh` 12 项全过；单序列路径的吞吐不得下降。
