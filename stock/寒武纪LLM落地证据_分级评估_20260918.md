## 0. 一句话结论

**有真实、可验证的证据表明大模型"能在"寒武纪芯片上跑起来（技术可行性成立，且在主流模型上达到与 H100 一致的精度）；但没有硬证据表明大模型在寒武纪上"大规模跑起来了"。**
推理侧停在**试点＋适配声明＋零星生产上线声明（全部无吞吐数字）**；训练侧**基本空白**。

## 2. 框架与软件栈适配

### 2.1 自研栈构成（厂商官方口径）
`Neuware`（基础软件平台，含 **CNNL** 算子库、**BANG C/BANGPy** 编程语言、**MagicMind** 图编译器、**CNToolkit**、**CNPerf**、**CNStream**）、`torch_mlu` / `torch_mlu_ops`、`vLLM-MLU`、`CNAgent`（算子生成智能体）。
来源：[寒武纪官网 MagicMind](https://cambricon.com/index.php?a=lists&catid=378)、[MLU370-X8 产品页](https://www.cambricon.com/index.php?m=content&c=index&a=lists&catid=406)、[新华财经 2026-04-26](https://m.cnfin.com/cmjj-lb//zixun/20260426/4404838_1.html)

### 2.2 开源社区活跃度（程序化实测，2026-09-18 经 GitHub API）

**寒武纪官方 org 仅 23 个公开仓库**，体量极小：

| 仓库 | Stars | Forks | 最后推送 |
|---|---|---|---|
| `triton-linalg` | 225 | 30 | 2025-02-07 |
| `mlu-ops` | 182 | 132 | 2026-09-02 |
| **`vllm-mlu`** | **120** | **10** | **2026-05-11** |
| `ffmpeg-mlu` | 63 | 12 | 2025-12-15 |
| `cambricon-k8s-device-plugin` | 61 | 15 | 2026-08-07 |

| `CNStream` | 55 | 13 | 2025-03-21 |
| `mlu-exporter` | 31 | 11 | 2026-08-07 |

- **`MagicMind` 与 `CNNL` 在 GitHub 上不存在公开仓库**（API 返回 `Not Found`）——核心编译器与算子库**并未开源**，与官网"开源兼容性"表述有落差。
- 对照量级：同期 vLLM 主仓 ~9.2 万 stars、SGLang ~3.6 万 stars。**`vllm-mlu` 的 120 stars / 10 forks 属于实验性项目体量，且非主流分发渠道。**

**vLLM 官方主仓对 MLU 的支持状态**：仅有**文档级** PR [#25942](https://github.com/vllm-project/vllm/pull/25942)（"[Doc] Add Cambricon MLU support"，2025-09-30），**并非真正的 backend 合并**；实际可用路径仍是寒武纪自维护的 fork `Cambricon/vllm-mlu`。
**SGLang**：MLU 后端**至今树外**；CI 基础设施 RFC #32300 **截至 2026-09-15 仍为 OPEN**。
**DeepSpeed / Megatron**：未找到寒武纪官方适配仓库或公开支持证据。

### 2.3 精度支持（FP8 / MoE / 长上下文 / KV Cache）
- **FP8**：**来源互相矛盾，未找到官方一手确认**。厂商通稿称"芯片原生支持主流低精度数据格式，无需额外转换"（[新华财经 2026-04-26](https://m.cnfin.com/cmjj-lb//zixun/20260426/4404838_1.html)）；但第三方分析明确指出思元 590"在 **FP8 混合精度计算**、软件生态适配等方面仍存差距"（[EEPW 2025-09-02](http://m.eepw.com.cn/article/202509/473481.html)）。注意：智源为绕开此问题，**把官方 FP8 权重反量化为 BF16** 才能在 MLU590 上运行——这本身是 FP8 支持不足的间接证据。
- **MoE**：有实现证据。FlagRelease R1 方案使用来自 **vLLM 的 Triton fused MoE** 算子（[FlagRelease R1 模型卡](https://huggingface.co/FlagRelease/DeepSeek-R1-FlagOS-Cambricon-BF16)）；**约 70% 算子由 Triton/FlagGems 提供**，而非原生 BANG 算子。
- **长上下文 / KV Cache / 并行**：厂商声明支持 TP/PP/SP/DP/EP 5D 混合并行、PD 分离、稀疏 Attention 加速（[新华财经 2026-04-26](https://m.cnfin.com/cmjj-lb//zixun/20260426/4404838_1.html)）；**无第三方验证、无性能数字**。

### 2.4 迁移成本（反面证据，多为开发者社区一手材料）
- 算子缺失须用 **BANG 手写或回退 CPU**；MMCV 需为 MLU 打补丁（issue #3068）。
- `torch_mlu` 全部 Issue 仅 3 条，且都是安装/编译问题——**社区规模小到没有能力问题被暴露**。
- 行业专家定性：郑纬民院士"国产 AI 芯片核心问题是**生态不够好**，如果生态好，性能做到 60% 也有人用"；某大厂高管（匿名）"我们欢迎所有的国产芯片，但**生态只能有一个主人**"。

### 3.3 训练 vs 推理——最关键的判断点

**🟥 决定性证据：寒武纪 CEO 被当面追问，拒绝正面回答。**

2026-08-12 业绩说明会上，投资者直接提问：
> "目前国产头部大模型，参数不断提升到 2 万亿以上，需要大量的训练卡进行训练，请问**国内这些主要的大模型，有无用公司的芯片进行训练？有还是没有？**"

陈天石的回应是新一代微架构与软件平台的**描述性套话，没有回答"有"或"没有"**。同期公司口径仅为"实现了**规模化训练技术的场景拓展**"——**纯定性，无任何数字**。
来源：[21 世纪经济报道 2026-08-13](https://m.21jingji.com/article/20260813/herald/4bb7d9c925787814e0f3c5c49fbc16a4.html)

**🟥 DeepSeek 官方技术报告不含寒武纪。**
DeepSeek V4 技术报告明确表述：**"我们在英伟达 GPU 和华为昇腾 NPU 两个平台上均验证了细粒度 EP 方案"**——硬件验证清单**只有英伟达＋昇腾**。DeepSeek API 价格页小字：*"受限于高端算力，目前 V4 Pro 的服务吞吐能力有限，预计下半年**昇腾 950 超节点**批量上市后价格大幅下调"*。
来源：经济观察报 2026-04-24 http://m.eeo.com.cn/2026/0424/850759.shtml

**🟥 千卡级第三方训练结果，寒武纪全部缺席。**
智源 FlagOS 六芯端到端**训练**验证（2026-03-27，https://hub.baai.ac.cn/view/53417 ）：
- ✅ 寒武纪**出现**："多芯覆盖：天数智芯、沐曦、**寒武纪**、海光、摩尔线程、昆仑芯六款芯片端到端训练验证"——但验证模型是 **Qwen3-0.6B**（最小），Triton 算子替换率 >80%，与英伟达基线偏差 <2%。
- ❌ 寒武纪**不出现在**任何千卡结果中：
  - 海光 BW **1024 卡** Qwen3-32B-AR：扩展效率 **99.63%**、**MFU 30.84%**
  - 沐曦 C550 **千卡** Qwen3-10B/30B；沐曦+NVIDIA 异构千卡：效率 **81.64%**
  - 天数 Aquila-70B 异构混训：**89.5% / 92.81%**
  - 摩尔线程 MTT S5000：**>90% 线性扩展**

→ **结论：有公开第三方可验证的寒武纪训练案例，但只到 0.6B 小模型端到端；无千卡、无 MFU、无扩展效率。**

**🟥 学术侧证据也停留在老旧硬件与非 LLM 负载。**
arXiv 程序化检索：提及 `Cambricon` 的论文仅 **11 篇**，`MLU370` 仅 **3 篇**，**`MLU590` 为 0 篇**。仅有的带绝对实测数字的论文，对比基线是 **NVIDIA Jetson AGX Xavier**（边缘芯片），而非 H100/昇腾。最接近的学术实测是 MLU370-X4 上 R1-Distill-Qwen-7B 的相对 TPS 提升（+23%/+27%，**无绝对值**）。学术第三方 benchmark 停留在 **2020 年的 MLU100 + CV 负载**（ResNet/DenseNet/ImageNet）。

## 4. 部署主体证据

### 4.1 三大运营商——🟥 最大集群是昇腾，不是寒武纪

**中国移动 2025-2026 年 AI 通用计算设备（推理型）集采**（2025-08-19 公示完毕）：
- 总额约 **51.12 亿元**，**7058 台**，6 个标包，9 家中标
- **标包生态只有两类：2058 套"类 CUDA 生态"设备 ＋ 5000 套 "CANN（华为昇腾）生态"设备**
- **没有任何寒武纪专项标包。** 注意"类 CUDA"≠ 寒武纪（寒武纪是 MLU 自有架构，非类 CUDA）
- 中标方：中兴 8.85 亿、河南昆仑 8.38 亿、四川华鲲振宇 6.67 亿、武汉长江计算 5.98 亿、新华三 5.49 亿、宝德 4.95 亿、软通 4.27 亿、浙江华启 3.56 亿、浪潮 2.97 亿
- 来源：[智东西 2025-08-19](https://www.163.com/dy/article/K7BC36UC051180F7.html)

### 6.4 "适配"只是 PR 而无生产部署
模式明确：**发适配公告＋不公布任何生产吞吐**。这是**系统性证据缺口**。

## 9. 最终分级判断与依据

### 结论：整体 **(c) 只有适配声明/PR**，推理侧可视为 **(c) 偏 (b) 弱端**，训练侧为 **(d)**

**推理侧：判 (c)，理由——**
- ✅ **技术可行性是 (a) 级硬证据**：智源 FlagRelease 公开 BF16 权重＋Docker 镜像＋可复核的精度对齐数据（GSM8K/MMLU/CEVAL 与 H100 齐平），证明 R1 级模型**确实能在 MLU590 上正确运行**。
- ✅ 存在真实采购与零星生产上线声明：河南农商银行**寒武纪算力设备采购**中标公示；青海移动 MLU590 上线 DeepSeek 满血版 671B；智谱称 GLM-4.6 在寒武纪实现 **FP8+Int4"投产"**。
- ❌ **但"大规模"不成立**：零第三方实测吞吐、零 MLPerf 提交、官方 fork 仅 120 stars、FlagRelease 中寒武纪仅 5/279 条且完全缺席全部旗舰新模型、所有"适配"公告通篇无吞吐数字。
- → **"能跑"已被证明；"大规模跑起来"未被证实。** 最接近生产的两条证据（青海移动、智谱 GLM-4.6）**都是无数字的厂商/运营商通稿**。

**训练侧：判 (d)，理由——**
- ❌ DeepSeek 官方 V4 技术报告硬件验证清单**只有英伟达＋昇腾**。
- ❌ CEO 被当面追问"有无用寒武纪芯片训练国内主要大模型"时**拒绝正面回答**。
- ❌ 千卡级第三方训练结果（含 MFU、扩展效率）**全部落在海光/沐曦/摩尔线程/天数，寒武纪 0 条**。
- ❌ 学术侧 `MLU590` 论文数 **0 篇**。
- △ 唯一正面证据是智源 FlagOS 的 **Qwen3-0.6B** 端到端训练验证——**0.6B 与"大模型训练"不是一回事**。

**给决策者的一句话**：
> 寒武纪在大模型上的证据形态是"**精度对齐可验证、性能数字全缺失、训练侧基本空白**"。把它当作**可用的推理补充算力（试点/边缘/特定场景）**有据可依；把它当作**已支撑头部大模型大规模生产推理或训练**的算力底座，**目前没有硬证据支持**。

## 10. 三条使用纪律

1. **不要把"适配"读成"部署"，不要把"部署"读成"高性能部署"**——全篇未找到寒武纪侧任何绝对吞吐数字。
2. **不要引用任何"590 达 H100 80% / A100 80–90% / H20 的 1.5 倍"类数字**——仅见于内容农场，无原始出处。
3. **"寒武纪集群闲置"没有直接证据**——只有行业整体与"国产异构算力池"层面的证据，引用时须保留该限定。
