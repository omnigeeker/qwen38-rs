[RFC] Add CI Infrastructure for the SGLang MLU Backend#32300
Copy link

Description

Issue body actions

1. Motivation

The SGLang MLU backend needs a CI mechanism to keep its functionality continuously usable. Changes to MLU-specific code, as well as changes to shared SGLang components used by the MLU backend, can introduce regressions. Relevant pull requests therefore need to trigger MLU tests so that functional correctness is validated before the changes are merged.

The MLU hardware and its supporting execution environment are accessible only from Cambricon's internal network and cannot be attached directly to GitHub-hosted runners. This RFC proposes a CI architecture that connects the public SGLang GitHub workflows to the internal Jenkins and MLU cluster while preserving the internal network boundary. The resulting CI lane makes MLU validation visible to the SGLang community and helps maintain the backend's functional availability as the project evolves.

2. Summary

This RFC proposes community-visible PR and Nightly CI infrastructure for the Cambricon MLU backend in SGLang. The integration connects GitHub Actions to an internally operated Jenkins and MLU cluster without exposing Jenkins or internal infrastructure to the public Internet.

The corresponding implementation is tracked in sgl-project/sglang#26898.

The proposed CI infrastructure has these properties:

  • Pull requests run only after the existing run-ci gate and MLU-related path filters pass.
  • During the initial observation period, the PR lane is a non-required check and does not block pull requests from being merged.
  • Test failures fail the GitHub job and remain visible as code-related failures.
  • Infrastructure failures and MLU resource queue timeouts are reported with a warning annotation, while the GitHub job concludes successfully because contributors cannot repair the private CI infrastructure.
  • Nightly and trusted manual/default-branch runs remain strict.
  • Results distinguish test failures, infrastructure failures, and timeouts.
  • Jenkins logs and structured result metadata are uploaded as GitHub artifacts when the GitHub job has started and reaches the upload step.
  • PR and Nightly jobs use separate labels in a dedicated runner group and run on one-job ephemeral self-hosted GitHub Actions runners on the VPS.
  • The PR workflow runs with pull_request_target, so its YAML and reusable gate come from the reviewed base branch.
  • The self-hosted runner never checks out or executes client code from the pull request.

The proposal is intended to begin with an observation period. It does not ask SGLang maintainers to make the MLU lane required at initial rollout.

3. Proposed Architecture

The architecture consists of four modules across three trust zones: public GitHub, the VPS, and the trusted internal network containing the controller, Jenkins, and MLU resources.

3.1 GitHub Community

The SGLang-side integration includes PR and Nightly workflows, the existing run-ci gate and path filters, and a reliability reporting workflow. GitHub Actions dispatches eligible MLU CI jobs and displays their status, annotations, logs, and artifacts to contributors.

3.2 VPS

The VPS hosts:

  • a GitHub Actions runner provisioner;
  • one PR runner slot and one Nightly runner slot;
  • a task submission bridge and task/status store;
  • a trusted, preinstalled sglang-mlu-ci client.

sglang-mlu-ci is an operator-installed command-line client invoked by the GitHub workflow. It submits validated task metadata, polls for progress, and publishes the final result without fetching or executing pull request code.

3.3 Internal Controller

The internal controller retrieves pending tasks from the VPS, coordinates their execution in Jenkins, and returns status and logs. It also provides a runner broker that issues restricted JIT configurations for ephemeral runners. GitHub Actions has no direct access to Jenkins or MLU resources, and communication with internal services is initiated from within Cambricon's network.

3.4 Jenkins / MLU Cluster

Jenkins receives the repository URL, immutable commit SHA, task ID, and trigger type. It checks out the exact SHA in an isolated MLU pod, prepares the MLU backend dependencies, and runs the registered PR or Nightly test suites. Execution status and logs are returned through the internal controller.

4. GitHub Workflow Policy

4.1 Trigger Policy

The workflow uses pull_request_target so the workflow definition and reusable gate are loaded from the reviewed base branch. It never checks out the pull request or executes repository code on the self-hosted runner. The untrusted repository URL and immutable head SHA are passed only as data to the trusted client, and PR code is executed later in the isolated Jenkins MLU pod.

The MLU PR job is entered only when:

  1. the PR targets main;
  2. the changed files match the MLU/shared-runtime path filters;
  3. the PR is not a draft;
  4. the PR has the run-ci label;
  5. the existing PR gate and rate-limit policy pass.

Important

SGLang maintainers must review and merge the MLU workflow files into the default branch before the PR and Nightly lanes can run. GitHub loads pull_request_target, schedule, and workflow_dispatch definitions from the default branch. This bootstrap also prevents a pull request from replacing the commands executed on the self-hosted runner.

4.2 Lane Isolation

The Organization runner group is named mlu-ci and is restricted to the SGLang repository. The jobs select it as follows:

# Pull requests
runs-on:
  group: mlu-ci
  labels: mlu-pr

# Nightly
runs-on:
  group: mlu-ci
  labels: mlu-nightly

Separate labels prevent a long Nightly GitHub job from occupying the PR runner slot. Each lane has one provisioner in the initial deployment, so the maximum GitHub-side concurrency is one PR job and one Nightly job.

4.3 Initial Observe-Only PR Policy

During the initial observation period, the MLU PR lane is a non-required check. Its result policy is:

Result GitHub annotation PR job conclusion Reason
Success none success MLU validation completed successfully.
test/pytest error failure A test executed and failed, indicating a possible code regression.
Invalid request or source metadata error failure The requested source cannot be safely or correctly tested.
infrastructure/* warning success Private CI infrastructure is unavailable and cannot be repaired by the contributor.
timeout/mlu_resource_queue warning success No MLU resource became available within the queue time budget.
timeout/external_task warning success The VPS task did not reach a terminal state within its active-task time budget.
timeout/github_client warning success The GitHub-side client did not receive a terminal result within its time budget.
timeout/jenkins_task error failure An executing Jenkins task exceeded its time budget, which may indicate a hung or regressed test.

Test failures remain visible as failing checks, but they do not block merging while the lane is non-required. Infrastructure failures conclude successfully with a warning because contributors cannot repair the private CI infrastructure.

timeout/jenkins_task remains a failure because it indicates that an executing test may have hung or regressed. MLU resource queue timeout is advisory because a contributor cannot make internal hardware available.

No automatic retry is proposed during the initial observation period. Returning a warning avoids blocking the PR, while not retrying prevents duplicate Jenkins work and makes infrastructure reliability visible in the data. An automatic single retry can be considered after the observation period.

Nightly, default-branch, and trusted manual runs use strict conclusions so infrastructure operators still receive a red signal when the lane is unhealthy.

5. Test Scope

PR validation currently uses:

  • pr-test-1-mlu: tests requiring one MLU device;
  • pr-test-2-mlu: tests requiring two MLU devices.

Additional test cases and suites can be added as MLU coverage requirements evolve. Nightly uses the independent nightly-test-mlu suite.

6. Failure Classification and Reporting

The status is not limited to pass/fail. The task result carries:

{
  "status": "error",
  "failure_type": "timeout",
  "failure_stage": "mlu_resource_queue",
  "observe_only": true,
  "github_conclusion": "success",
  "task_id": "<task-id>"
}

The main classifications include:

Failure type Example stages Meaning
test pytest A test executed and failed
infrastructure jenkins_connect, internal_poller, runner_client, vps_bridge CI infrastructure could not execute or report the test normally
timeout mlu_resource_queue, jenkins_task, external_task, github_client A named layer exceeded its time budget
request task_submission The submitted repository/ref/SHA metadata was invalid

The classification is emitted in four places:

  1. the live Actions console log;
  2. a GitHub warning or error annotation;
  3. the GitHub step summary;
  4. result-<task-id>.json in the uploaded artifact.

An example line is:

MLU CI failure classification: type=timeout, stage=mlu_resource_queue

7. Log Streaming, Artifact Upload, and Retention

The internal master incrementally reads the Jenkins console log and sends log chunks to the VPS task store. The trusted client polls for new log bytes and prints them to the GitHub Actions console. At terminal status, it downloads the complete log and writes:

jenkins-<task-id>.log
result-<task-id>.json

The workflow upload step uses if: always() and actions/upload-artifact@v4. Result metadata is also uploaded as a separate small mlu-ci-result-pr-<run-id>-<attempt> artifact with 30-day retention, so the weekly reporter does not need to download the complete Jenkins log.

Artifact upload is best-effort rather than unconditional. It works for normal success, test failure, classified infrastructure failure, and classified timeout after the GitHub job has started. It cannot run when:

  • no runner ever claims the GitHub job;
  • the runner host or runner process is terminated before the upload step;
  • GitHub's artifact service itself is unavailable.

To provide a recovery window, failed tasks and their logs remain on the VPS for 72 hours by default. The duration is configurable by the operator. Successful tasks are removed after complete log download. A successful task with incomplete log download is also retained for the recovery window. GitHub artifact retention remains controlled by the SGLang repository's Actions retention setting.

8. Timeout Budget

The PR timeout budget is intentionally ordered from the execution layer outward:

Layer PR timeout
Internal poller claim 5 minutes
Continuous Jenkins unavailability 5 minutes
Jenkins pipeline, including MLU resource wait 100 minutes
VPS active task 105 minutes
Trusted GitHub client 110 minutes
GitHub Actions job 120 minutes

This leaves time for the inner layer to publish a classified terminal result and for outer layers to drain logs and upload artifacts.

Nightly has an independent longer budget:

Layer Nightly timeout
Jenkins Nightly task 420 minutes
VPS active task 435 minutes
Trusted GitHub client 450 minutes
GitHub Actions job 480 minutes

9. Ephemeral Runner Provisioning

Each ephemeral runner requires a fresh GitHub JIT configuration, and the GitHub API that issues this configuration requires Organization-level self-hosted runner management permission. To keep this permission off the VPS, an internal broker uses a GitHub App with only:

Organization permission: Self-hosted runners, read and write
Repository permissions: no additional permissions

The broker fixes the Organization, runner group, and allowed lane labels. The VPS can request only an mlu-pr or mlu-nightly JIT configuration and cannot use the broker to create runners with arbitrary access. The GitHub App credentials remain inside the internal network.

Each runner is configured as ephemeral and processes at most one GitHub job. After it exits, the provisioner uses the broker to remove the old registration and obtain a JIT configuration for its replacement. Stale registrations are also removed without affecting runners outside the configured group and label boundary.

The expected steady state is two registered runners: one PR runner and one Nightly runner. Runner IDs changing after jobs is expected; an ever-growing list of offline runners is not.

Important

Production rollout requires cooperation from sgl-project Organization administrators to authorize the restricted mlu-ci runner group and install the runner-provisioning GitHub App. SGLang repository maintainers must also keep the MLU PR check non-required during the initial observation period, as described in Section 4.3.

10. Security Model

10.1 GitHub Permissions and Credentials

  • The workflows declare explicit, minimal, read-only GITHUB_TOKEN permissions.
  • No repository write credential is installed on the self-hosted runner or passed to pull request code.
  • The runner-provisioning GitHub App has no repository permissions; it has only the Organization-level self-hosted runner permission required to manage ephemeral runners.
  • The VPS has no GitHub Organization credential and can request runners only for the predefined MLU runner group and lane labels through the broker.

As a result, the MLU CI infrastructure cannot modify repository code, pull requests, or issues. An infrastructure outage can affect only the availability and reporting of the MLU lane. A compromise of the runner-provisioning GitHub App could affect Organization runner registrations, but it would not grant access to repository content or repository write operations.

10.2 Trusted Runner Code

The self-hosted job does not run actions/checkout for the pull request. It invokes a preinstalled sglang-mlu-ci command deployed from a trusted infrastructure revision. The workflow passes only validated metadata: repository name, GitHub HTTPS clone URL, and full commit SHA.

The pull_request_target workflow and its local reusable gate are loaded from the base branch. A pull request therefore cannot replace the run: block that invokes the trusted client. The workflow has explicit read-only permissions and does not expose repository or infrastructure secrets.

The pull request code is fetched and executed only inside the isolated Jenkins MLU pod. Jenkins checks out the immutable SHA and verifies that HEAD matches it.

10.3 Remaining Trust Assumptions

  • The VPS, internal controller, Jenkins, and MLU pod isolation are managed by the Cambricon MLU CI maintainers and are treated as trusted infrastructure in this proposal.
  • The MLU workflow on the default branch has passed normal SGLang review.
  • The dedicated runner group remains restricted to the intended repository/workflow.

11. Operations and Response SLA

The proposed primary community contact is @chenxb002.

The response target applies to infrastructure-classified failures, repeated MLU resource queue timeouts, and runner unavailability. It does not apply to test failures caused by the code under test.

During the observe-only period, the Cambricon MLU CI maintainers will:

  • acknowledge a reported or monitored infrastructure incident within one business day;
  • restore the affected lane, temporarily disable it, or publish a status update within two business days (worst case);
  • publish a follow-up when service is restored.

While an infrastructure incident remains unresolved, the PR lane remains non-required and infrastructure-classified results do not block pull requests.

These are proposed response targets rather than an uptime guarantee and should be confirmed by the named contact and SGLang maintainers during RFC review.

12. Reliability Visibility

Infrastructure failures remain visible even when the PR conclusion is successful. A scheduled workflow aggregates only PR-lane runs and appends a reliability report to the public RFC issue. The report is published weekly while the lane remains observe-only.

The report includes:

  • total triggered, started, completed, cancelled, and unclaimed jobs;
  • success and test-failure counts;
  • counts grouped by failure_type and failure_stage;
  • MLU queue timeout count;
  • median and p95 queue/completion time where available;
  • artifact and structured metadata coverage among jobs that started.

Failure classifications come from the structured result artifact and are combined with GitHub run and job metadata. Jobs that never receive a runner or never upload result metadata are reported separately rather than silently excluded, allowing the community to distinguish runner assignment, reporting coverage, and classified CI reliability.

The reporter runs only on GitHub-hosted runners. Report collection is read-only, while a separate publishing job receives issues: write only to append the report comment; the MLU PR workflow remains read-only. Every report is also available in the step summary and as Markdown/JSON artifacts. Each run creates a new issue comment so the community can compare historical snapshots.

13. Demonstrated Behavior

Note

The following evidence was collected in the public sglang-mlu/sglang fork, which deploys the trusted-workflow, observe-only policy, and ephemeral-runner architecture proposed in this RFC. All demo pull requests, workflow runs, jobs, annotations, and artifacts linked in this section come from that fork.

13.1 Successful PR Run

The final trusted-workflow and ephemeral-runner architecture successfully validated pull request #5:

  • workflow run, triggered by pull_request_target for commit 58bef9b52280d8637867bdb7e64608c35d8e2f4d;
  • pr-test-mlu job, completed successfully on an ephemeral runner with label mlu-pr in the dedicated mlu-ci runner group;
  • the MLU task, result metadata upload, and Jenkins log upload steps all completed successfully;
  • both mlu-ci-result-pr-30064140061-1 and mlu-jenkins-log-pr-30064140061-1 artifacts were created.

13.2 Successful Nightly Run

The strict Nightly lane successfully validated the same commit:

  • workflow run, manually triggered for commit 58bef9b52280d8637867bdb7e64608c35d8e2f4d;
  • nightly-test-mlu job, completed successfully on an ephemeral runner with label mlu-nightly in the dedicated mlu-ci runner group;
  • the Nightly MLU task and Jenkins log upload steps both completed successfully;
  • the mlu-jenkins-log-nightly-30064649714-1 artifact was created.

13.3 Intentional Test Failure

Pull request #6 added a deterministic failing test to verify that a pytest failure remains red and is propagated through Jenkins:

  • workflow run, triggered by pull_request_target for commit 2400a0a9cd73c11540923a765787f4ce53fc2c2b;
  • pr-test-mlu job, failed as expected while both artifact upload steps completed successfully;
  • the Actions log identified TestMLUCIFailureDemo::test_intentional_failure_reaches_github_actions and showed the intentional AssertionError;
  • the failure annotation reported MLU CI failure classification: type=test, stage=pytest;
  • both mlu-ci-result-pr-30065563358-1 and mlu-jenkins-log-pr-30065563358-1 artifacts were created.

This confirms that observe-only handling does not mask test failures: a code-related test failure still produces a failing GitHub conclusion.

13.4 Jenkins Unavailable

Pull request #7 validated the observe-only behavior when the internal controller could not connect to Jenkins. For this experiment, the controller was temporarily pointed at an unreachable local endpoint; the Jenkins service itself was not stopped:

  • workflow run, triggered by pull_request_target for commit 42bfa1145c3a6a770a923844ccb954fb754dc1a3;
  • pr-test-mlu job, completed successfully after the five-minute Jenkins availability deadline;
  • the warning annotation reported MLU CI failure classification: type=infrastructure, stage=jenkins_connect;
  • the MLU task step and both artifact upload steps completed successfully under the observe-only policy;
  • both mlu-ci-result-pr-30068996587-1 and mlu-jenkins-log-pr-30068996587-1 artifacts were created.

This confirms that an internal Jenkins outage remains visible as a warning and structured infrastructure result without making the contributor's PR job fail.

13.5 MLU Resource Queue Timeout

Pull request #8 validated the observe-only behavior when Jenkins accepted the build but could not schedule an MLU worker. For this experiment, the pipeline temporarily used an unavailable MLU label and a five-minute outer timeout:

  • workflow run, triggered by pull_request_target for commit a01f381b84b04c5e28197e2f88669c0f3515f240;
  • pr-test-mlu job, completed successfully after the Jenkins resource queue timeout;
  • the warning annotation reported MLU CI failure classification: type=timeout, stage=mlu_resource_queue;
  • the MLU task step and both artifact upload steps completed successfully under the observe-only policy;
  • both mlu-ci-result-pr-30069671544-1 and mlu-jenkins-log-pr-30069671544-1 artifacts were created.

This confirms that unavailable internal MLU capacity remains visible as a classified timeout without blocking the contributor's PR.

13.6 Internal Poller Unavailable

Pull request #9 validated the observe-only behavior when the VPS accepted a task but the internal controller was unavailable to claim it. For this experiment, only the internal task poller was stopped; the GitHub runner, VPS services, runner broker, and Jenkins remained available:

  • workflow run, triggered by pull_request_target for commit 1ff76ae934036c7aed99d497b35c60b327d824b1;
  • pr-test-mlu job, completed successfully after the five-minute task claim deadline;
  • the warning annotation reported MLU CI failure classification: type=infrastructure, stage=internal_poller;
  • no Jenkins build was created because the task was never claimed by the internal controller;
  • both mlu-ci-result-pr-30070992748-1 and mlu-jenkins-log-pr-30070992748-1 artifacts were created.

This confirms that an unavailable internal poller is reported as a visible infrastructure warning without blocking the contributor's PR or silently losing the task.
